# Модель вимог та варіантів використання

## Функціональні вимоги (EARS)

| ID | Вимога |
|---|---|
| FR-1 | WHEN користувач або гість відкриває каталог, система SHALL показати записи `ANIME` з атрибутами `title`, `synopsis` і `release_date`. |
| FR-2 | WHEN користувач або гість фільтрує каталог за жанром, система SHALL показати записи `ANIME`, пов'язані з відповідним записом `GENRE` через зв'язок `ANIME }o--o{ GENRE : has`. |
| FR-3 | WHEN користувач (`USER`) задає статус аніме, система SHALL створити або оновити пов'язаний запис `USER_ANIME_STATUS` через зв'язки `USER ||--o{ USER_ANIME_STATUS` та `ANIME ||--o{ USER_ANIME_STATUS`, зберігши атрибути `status` (лише «дивлюсь», «в планах» або «переглянуто») і `last_updated`. |
| FR-4 | IF гість, який не має запису `USER`, намагається змінити статус аніме, система SHALL відхилити дію та не створювати зв'язок `USER`—`USER_ANIME_STATUS`. |
| FR-5 | WHEN користувач (`USER`) публікує відгук для аніме, система SHALL створити запис `REVIEW` з атрибутами `score`, `text` і `created_at`, пов'язаний із користувачем через `USER ||--o{ REVIEW : writes` та з аніме через `ANIME ||--o{ REVIEW : receives`. |
| FR-6 | IF гість, який не має запису `USER`, намагається опублікувати відгук, система SHALL відхилити дію та не створювати зв'язок `USER`—`REVIEW`. |
| FR-7 | WHEN зовнішній API постачає дані для синхронізації, система SHALL створити або оновити записи `ANIME` (`title`, `synopsis`, `release_date`) і `GENRE` (`name`), а також зв'язок `ANIME }o--o{ GENRE : has` відповідно до даних API. |

## User stories

- **US-1 — Перегляд каталогу:** Як користувач або гість, я хочу переглядати каталог аніме за жанрами, щоб знаходити цікаві тайтли.
- **US-2 — Статус перегляду:** Як зареєстрований користувач, я хочу позначати статус перегляду аніме, щоб вести особистий список.
- **US-3 — Відгук:** Як зареєстрований користувач, я хочу оцінювати аніме та публікувати текстовий відгук, щоб ділитися своєю думкою.
- **US-4 — Актуальний каталог:** Як користувач каталогу, я хочу, щоб дані про аніме та жанри синхронізувалися із зовнішнім API, щоб каталог містив актуальну інформацію.

## Сценарії прийняття (Gherkin)

### SC-1 — Перегляд каталогу

```gherkin
Feature: Перегляд каталогу аніме

  Scenario: Користувач переглядає тайтли вибраного жанру
    Given користувач відкрив каталог аніме
    When користувач обирає жанр
    Then система показує записи ANIME з атрибутами title, synopsis і release_date
    And кожен показаний тайтл пов'язаний із вибраним записом GENRE зв'язком has
```

### SC-2 — Оновлення статусу перегляду

```gherkin
Feature: Особистий список перегляду

  Scenario Outline: Користувач задає статус аніме
    Given користувач увійшов у систему
    And користувач відкрив сторінку аніме
    When користувач задає статус "<status>"
    Then система створює або оновлює запис USER_ANIME_STATUS зі статусом "<status>"
    And запис пов'язаний із користувачем через USER
    And запис пов'язаний із тайтлом через ANIME

    Examples:
      | status       |
      | дивлюсь      |
      | в планах     |
      | переглянуто  |

  Scenario: Гість намагається змінити статус
    Given гість відкрив сторінку аніме
    When гість намагається змінити статус перегляду
    Then система відхиляє дію
    And система не створює запис USER_ANIME_STATUS без пов'язаного USER
```

### SC-3 — Публікація відгуку

```gherkin
Feature: Відгуки про аніме

  Scenario: Користувач публікує відгук з оцінкою
    Given користувач увійшов у систему
    And користувач відкрив сторінку аніме
    When користувач надсилає оцінку та текст відгуку
    Then система створює запис REVIEW з оцінкою score та текстом text
    And REVIEW пов'язаний із USER зв'язком writes
    And REVIEW пов'язаний із ANIME зв'язком receives

  Scenario: Гість намагається опублікувати відгук
    Given гість відкрив сторінку аніме
    When гість намагається надіслати відгук
    Then система відхиляє публікацію
    And система не створює запис REVIEW без пов'язаного USER
```

### SC-4 — Синхронізація каталогу

```gherkin
Feature: Синхронізація каталогу аніме

  Scenario: Система синхронізує тайтли та жанри із зовнішнім API
    Given зовнішній API доступний і надає дані про тайтли та жанри
    When система запускає синхронізацію каталогу
    Then система створює або оновлює ANIME з атрибутами title, synopsis і release_date
    And система створює або оновлює GENRE з атрибутом name
    And система встановлює зв'язок has між відповідними записами ANIME і GENRE
```

## Діаграма варіантів використання

Зв'язок узагальнення спрямований від спеціалізованого актора `User` до базового `Guest`: зареєстрований користувач успадковує можливість перегляду каталогу. Стрілка `<<include>>` спрямована від основного use case до обов'язкового підсценарію; `<<extend>>` — від умовного розширення до базового use case.

```mermaid
flowchart LR
    Guest[Гість]
    User[Зареєстрований користувач]
    API[Зовнішній API]

    subgraph System[Система обліку аніме]
        UC1([UC-1: Перегляд каталогу])
        UC1a([Показати тайтли та жанри])
        UC1b([Фільтрувати каталог за жанром])
        UC2([UC-2: Оновити статус перегляду])
        UC2a([Вибрати статус])
        UC3([UC-3: Опублікувати відгук])
        UC3a([Ввести оцінку та текст])
        UC4([UC-4: Синхронізувати каталог])
        UC4a([Імпортувати тайтли та жанри])
    end

    User -.->|узагальнення| Guest
    Guest --- UC1
    User --- UC2
    User --- UC3
    API --- UC4

    UC1 -.->|&lt;&lt;include&gt;&gt;| UC1a
    UC1b -.->|&lt;&lt;extend&gt;&gt;: жанр обрано| UC1
    UC2 -.->|&lt;&lt;include&gt;&gt;| UC2a
    UC3 -.->|&lt;&lt;include&gt;&gt;| UC3a
    UC4 -.->|&lt;&lt;include&gt;&gt;| UC4a
```

## ER-діаграма

```mermaid
erDiagram
    USER {
        UUID id PK
        string username
        string email
        datetime register_date
    }

    ANIME {
        UUID id PK
        string title
        text synopsis
        datetime release_date
    }

    REVIEW {
        UUID id PK
        UUID user_id FK
        UUID anime_id FK
        number score
        text text
        datetime created_at
    }

    GENRE {
        UUID id PK
        string name
    }

    USER_ANIME_STATUS {
        UUID id PK
        UUID user_id FK
        UUID anime_id FK
        string status
        datetime last_updated
    }

    USER ||--o{ REVIEW : writes
    ANIME ||--o{ REVIEW : receives
    ANIME }o--o{ GENRE : has
    USER ||--o{ USER_ANIME_STATUS : has
    ANIME ||--o{ USER_ANIME_STATUS : linked_to
```
