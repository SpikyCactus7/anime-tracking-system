# DEFENSE — Завдання 2: Вимоги та Use Cases

## Намір і критерії (1–2 речення):
Сформувати узгоджену з існуючою ER-моделлю систему функціональних вимог (EARS), user stories, Gherkin-сценаріїв, матрицю трасування M:N, та use case діаграму для системи відстеження аніме. 
Ключові критерії: однозначність і тестованість вимог, ≥2 типів акторів з узагальненням, коректне використання include/extend та явне позначення непокритих вимог (out-of-scope).

## Топ-3 розбіжності (spec ↔ артефакт) + коміт-виправлення:
* Перша версія містила двозначні вимоги EARS без прив'язки до полів ER-моделі, а UC діаграма не мала include/extend та узагальнення акторів. Виправлено уточненням критеріїв у spec.md (коміт: added include/extend to UC diagram and aligned EARS with ER diagram).
* ШІ використав include для елементарних дій UI ("Вибрати статус", "Ввести оцінку") замість виділення спільної поведінки. Виправлено уточненням критерію використання include (коміт: fixed UC include relations, added M:N matrix and uncovered requirement).
* У матриці трасування були відсутні зв'язки багато-до-багатьох та out-of-scope вимоги. Виправлено доданням вимоги авторизації FR-8 (пов'язаної одразу з UC-2 та UC-3) та непокритої вимогу FR-9 щодо email-сповіщень з обґрунтуванням (коміт: fixed UC include relations, added M:N matrix and uncovered requirement).

## Ключове рішення — які альтернативи зважив і чому обрав цю (ADR):
ADR-001: Визначення меж сценаріїв використання, виділення перевірки авторизації у спільний include та винесення email-сповіщень в out-of-scope
* Статус: Прийнято
* Контекст і проблема: Необхідно вирішити, як правильно розбити систему на use cases, при цьому не дублювати перевірку прав у зміні статусу (UC-2) та відгуках (UC-3), не перевантажувати діаграму елементарними UI кроками і вирішити, як обробляти атрибут USER.email із моделі даних, створеної в завданні 1.
* Розглянуті альтернативи:
  1. Створити окремі use cases для кожного кроку зі зв'язками include, реалізувати email-розсилку в поточній версії
  2. Об'єднати перегляд каталогу, фільтрацію, зміну статусу та написання відгуків в єдиний сценарій "Взаємодія з тайтлом".
  3. Розділити прецеденти за атомарними цілями акторів, винести умовну фільтрацію в extend, виділити перевірку авторизації у спільний обов'язковий підсценарій include, а вимогу щодо email-сповіщень (FR-9) зафіксувати як непокриту (out-of-scope).
* Рішення: Обрано альтернативу 3.
* Обґрунтування: Альтернатива 1 перетворює UC діаграму на блок-схему алгоритму і збільшує обсяг через потребу інтеграції зовнішнього SMTP-сервісу для FR-9. Альтернатива 2 ускладнює встановлення межі між гостем і зареєстрованим користувачем. Альтернатива 3 чітко відокремлює публічні сценарії (Guest) від захищених (User), усуває дублювання через зв'язок M:N, оскільки одна вимога FR-8 покриває і UC-2, і UC-3, та зберігає трасованість атрибута `USER.email` без затримки релізу.
* Наслідки:
  * Позитивні: Логіка доступу не дублюється, діаграма та матриця трасування залишаються прозорими й читабельними.
  * Негативні / Компроміси: Вимога FR-9 залишається непокритою в поточній версії та має бути імплементована в наступних релізах.

## Перевірка — узгодженість із попередньою моделлю (як перевірив):
Викнонав звірку усіх вимог EARS та Gherkin-сценаріїв із сутностями та атрибутами ER-діаграми із завдання 1:
* Усі поля у вимогах (наприклад, статуси, оцінки, дати) повністю збігаються з таблицями USER, ANIME, REVIEW, GENRE та USER_ANIME_STATUS.
* Логіка розподілена за ролями, тобто неавторизований гість не може створити запис, де потрібен ID користувача (відгуки чи статуси), цілісність зв'язків не порушується.
